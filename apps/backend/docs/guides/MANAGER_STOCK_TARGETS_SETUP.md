# Setting up the Manager stock targets in production

Scanner sends nothing to Manager until the targets exist. There is no UI for this —
it is three API calls, once per shop. This guide is the whole procedure.

For the management API in general (list, disable, remove) see
[OUTBOUND_WEBHOOK_GUIDE.md](./OUTBOUND_WEBHOOK_GUIDE.md); this one covers only what
the Manager stock integration needs.

---

## Before you start

You need four things:

1. **Manager's base URL**, for example `https://manager.example.com`.
2. **The shared API key.** One value, generated by you, given to both applications.
   On Manager's side it is stored as `MANAGER_API_KEY_TO_LOCATION_TRACKER_APP`. It is
   *not* `LOCATION_TRACKER_API_KEY` (that is the key Manager uses to call Scanner).
   Minimum 16 characters — use far more.
3. **An admin account on Scanner** that is linked to the shop you are configuring.
4. **The outbound worker running.** `shopify-outbound-webhook-worker` in the EC2
   deploy script. Without it nothing is ever sent, and no error appears anywhere.

The key is **per shop**. One key = one Scanner shop = one Manager workspace. Scanner
sends no shop or tenant id — Manager identifies the sender by the key alone.

---

## Step 1 — get an admin access token

The management endpoints use the normal user auth stack: a bearer token from a login,
admin role, linked shop. They do **not** use `EXTERNAL_API_KEY`.

```bash
BASE=https://your-scanner-domain.com

TOKEN=$(curl -s -X POST "$BASE/api/auth/login" \
  -H "Content-Type: application/json" \
  -d '{"username":"your-admin","password":"your-password"}' \
  | python3 -c 'import sys,json; print(json.load(sys.stdin)["tokens"]["accessToken"])')

echo "${TOKEN:0:12}…"
```

Access tokens are short-lived. If a later call returns 401, log in again.

---

## Step 2 — register the three targets

Same endpoint three times, once per event type. `label` is free text for humans;
`secret` is the shared key from above — **the same value in all three**.

```bash
MANAGER=https://manager.example.com
KEY='the-shared-api-key'

register () {
  curl -s -X POST "$BASE/api/outbound-webhooks" \
    -H "Authorization: Bearer $TOKEN" \
    -H "Content-Type: application/json" \
    -d "{\"label\":\"$1\",\"targetUrl\":\"$2\",\"secret\":\"$KEY\",\"eventType\":\"$3\"}"
  echo
}

register "manager-stock-demand" \
  "$MANAGER/api/v1/location-tracker/webhooks/stock-demand" \
  "stock_demand"

register "manager-stock-demand-deleted" \
  "$MANAGER/api/v1/location-tracker/webhooks/stock-demand-deleted" \
  "stock_demand_deleted"

register "manager-items-processed" \
  "$MANAGER/api/v1/location-tracker/webhooks/items-processed" \
  "items_processed"
```

Each returns `201` with `{"id":"cm…"}`.

### What each one does

| `eventType` | Sent when | Consequence of leaving it out |
|---|---|---|
| `stock_demand` | a stock rule changes (targeted delta), worker startup, and full snapshots at 07:00, 12:00 and 17:00 Stockholm time | **Nothing is sent at all.** With no demand target the whole sync is a deliberate no-op — silent, by design |
| `stock_demand_deleted` | a rule is gone and its identity has to be withdrawn | Demand still flows, but each sync writes a `skipped` row with `no_delete_target` and Manager keeps asking for stock you no longer track |
| `items_processed` | a ScanHistory record is created (an article was handled) | Manager is never told an item was processed |

Register **exactly one** of each per shop. Two active targets of the same type make
the sync refuse to run and write a `skipped` row with `ambiguous_targets` — a
deliberate stop, not a crash, because Scanner cannot know which one is right.

## Step 3 — confirm it worked

```bash
# The three targets, active. `secret` is never returned.
curl -s "$BASE/api/outbound-webhooks" -H "Authorization: Bearer $TOKEN"

# What actually went out. A stock edit sends a targeted delta immediately; full
# recovery snapshots run at the configured Stockholm-time schedule.
curl -s "$BASE/api/outbound-webhooks/deliveries?limit=20" \
  -H "Authorization: Bearer $TOKEN"

# What Manager is believed to hold.
curl -s "$BASE/api/outbound-webhooks/manager-stock" \
  -H "Authorization: Bearer $TOKEN"
```

Don't wait for the interval if you want an immediate answer: edit any stock rule's
threshold. That triggers a sync straight away.

### Reading the delivery rows

| `status` | Meaning |
|---|---|
| `delivered` | Manager answered 2xx and the body parsed |
| `rejected` | Manager refused. `responseStatus` 401 = wrong key; 422 = Scanner sent something Manager considers malformed |
| `failed` | network error, timeout, or 5xx — retried automatically |
| `pending` | queued, not yet answered. Older than 5 minutes means it never reached Redis |
| `skipped` | Scanner decided not to send. `lastError` says why |

`lastError` values worth recognising: `ambiguous_targets` (two active targets of one
type), `no_delete_target` (no `stock_demand_deleted` target registered),
`no_article_number` (a scan had a blank barcode, so no report could be built).

## Rotating the key

Register the same URL and event type again with the new secret. The endpoint upserts
on `(shop, targetUrl, eventType)`, so the row is updated rather than duplicated, and
the secret is read **at send time** — the next attempt already uses the new key. No
redeploy, no restart.

One catch: `POST` returns **409** if an *active* target already exists for that URL
and event type. To rotate, disable it first, then re-register:

```bash
curl -s -X PATCH "$BASE/api/outbound-webhooks/TARGET_ID/active" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"active":false}'
# then POST again with the new secret — it comes back active
```

Anything rejected with 401 while the key was wrong is re-sent automatically on the
next tick, for up to 7 days, at most 200 per tick.

---

## When something is wrong

| Symptom | Likely cause |
|---|---|
| No delivery rows at all, ever | No `stock_demand` target, or the outbound worker is not running |
| Every row `rejected` / 401 | Key mismatch — Manager has a different value, or has not been configured yet |
| Rows `rejected` / 422 | Scanner sent a body Manager rejects. `responseBody` carries Manager's message; this is a contract bug, not a config one |
| Rows stuck `pending` | Redis unreachable at trigger time. They are re-driven once it is back |
| `skipped` / `ambiguous_targets` | Two active targets of one type — disable one |
| 401 from Scanner's own API | Your admin access token expired; log in again |

Secrets never appear in delivery rows, logs or API responses, so a delivery row is
always safe to paste into a ticket.
